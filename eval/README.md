# Evaluation

Two separate evaluations, for two separate components. Results are written to [`results/`](results/) and are exactly reproducible.

## 1. Classification (`npm run eval`)

**Component:** the classifier plus the deterministic policy applied at intake (final state, action type, authority).

**Cases:** hand-written, labeled operational events. Each has an expected Situation Model state and expected action type.

| File | Cases | Role |
| --- | --- | --- |
| [`cases.dev.json`](cases.dev.json) | 30 | Used while writing the rules classifier (in-sample) |
| [`cases.holdout.json`](cases.holdout.json) | 40 | Written after the rules were frozen, run once, rules not changed afterward |

**Rules classifier, held-out set:** state accuracy 29/40 (72.5%), action type accuracy 29/40 (72.5%), 5 cases where an action that needs approval or a human was not recognized (read as `none`). An item whose action is `none` has no external action, so it cannot execute. The cost of that miss is routing (the item sits in `NOW` instead of `DECISIONS`), not an unauthorized action. Full confusion matrix and every miss: [`results/classification-holdout-rules.md`](results/classification-holdout-rules.md).

**Claude classifier: not yet measured.** Run `npm run eval -- --classifier llm` with `ANTHROPIC_API_KEY` set. The script reports how many cases fell back to rules.

**Does not show:** accuracy on real operational traffic. Both sets were written by the same author, and 40 cases is a small sample.

## 2. Control path under fault injection (`npm run eval:scenarios`)

**Component:** the deterministic engine and the simulated dispatch service. The classifier is bypassed: items are created directly with a known action type.

**Workload:** generated by a seeded pseudo-random generator, so it is randomized but exactly reproducible. Default: **1,000 items per seed, seeds 1, 7 and 123** (3,000 items total).

For each item:

| Draw | Distribution |
| --- | --- |
| Action type | uniform over 7 action types: 2 autonomous, 3 approval-required, 2 human-only |
| Human approves (approval-required only) | 80% |
| Operator executes a gated item before approval | 50% |
| Fault on the authorized execution | 55% none, 15% external failure, 15% timeout (settles to success on the next status read), 15% crash after the external success |
| Operator clicks Execute again immediately | 50% |

Unauthorized items always get one execution attempt. Reconciliation runs twice at the end.

**Failure definition.** An item fails if, after reconciliation, any of these is true:

| Code | Failure |
| --- | --- |
| F1 | The dispatch ledger shows a side effect for a human-only item, or an approval-required item that was never approved |
| F2 | The dispatch ledger shows more than one side effect for the item |
| F3 | The item's external result was lost (crash) or unknown (timeout) and the engine never logged `stale_detected` for it |
| F4 | The Situation Model's "closed as succeeded" disagrees with the dispatch ledger's "succeeded" |

**Result:** 0 failed items across 1,000 evaluated items on each of the three seeds. The same workloads through a naive executor (no authority check, no stable idempotency key, no reconciliation) fail 540, 533 and 571 items. That confirms the F1, F2 and F4 checks can detect failures. See [`results/control-path.md`](results/control-path.md) for per-seed counts.

**Does not show:**
- Anything about classification quality. The classifier is not in this loop.
- Behavior against a real external API. The dispatch service is a simulation with idempotent keys and exactly one crash point (after the external success, before the result is persisted).
- Concurrency. Requests are processed sequentially in one process, and parallel executes of the same item were not load-tested.
- Production reliability. It shows that these invariants held for these generated workloads.
